Memory for coding agents that carries over between sessions.

Collivind keeps what your agents learn (decisions, errors, patterns, facts about your code) in a local knowledge graph with vector search, and puts the relevant part back in front of the agent when you type a prompt.

Install in two commands View source on GitHub

Automatic recall in Claude Code and Codex; the memory tools also work in opencode and GitHub Copilot. MIT licensed. Runs on your machine.

Every new session starts from zero.

You explain the same storage decision on Monday and again on Thursday. The agent hits an error it already debugged last week and debugs it again. Context compaction drops the detail you needed an hour later. Switching from Claude Code to Codex loses all of it.

Collivind is a store outside the session. Agent sessions read from it and write to it, so what one session learned is there for the next: automatically in Claude Code, Codex and opencode, and in Copilot when you ask it to search or save.

How it works

Hooks in your agent do the reading and ask for the writing. The memory itself is a graph plus vectors on your disk.

  1. Recall on every prompt

    In Claude Code and Codex, a hook at session start injects a short index of what is stored for the project (about 100 tokens). On each prompt you type, another hook searches memory with it and adds the matches, within a token budget, and adds nothing when nothing matches.

  2. Checkpointed capture

    Every 15 responses (configurable) the agent is asked to save what it learned through the collivind_batch_add tool. A checkpoint counts as saved only when that call arrives; an unanswered one is re-asked with backoff and then recorded as failed. After a context compaction, the agent is asked to save from the summary.

  3. Graph plus vectors

    Memories are typed (fact, decision, pattern, error, architecture, preference, snippet) and linked to entities such as files, services and libraries. Search mixes vector similarity (70%) with graph proximity (30%). A newer version of a memory supersedes the old one and keeps the history; conflicting memories are linked as contradictions.

Local-first
Docker mode runs Qdrant, Neo4j and an embedding service in containers on your machine. Embedded mode needs no Docker: SQLite for vectors and graph, with the embedding model loaded in-process.
No LLM API keys
Embeddings are computed locally. Extracting memories from a conversation is done by the agent you already run, through its own model, so Collivind adds no model bill.
Plain tools
13 MCP tools for agents, and a CLI for you: search, add, update, invalidate, export, import, migrate, sync.

Install in two commands

Collivind is not on PyPI yet, so you install the wheel from the GitHub release.

# v0.12.0, the latest release
uv tool install https://github.com/maiiasleptcova/collivind/releases/download/v0.12.0/collivind_memory-0.12.0-py3-none-any.whl
collivind init

No Docker? Embedded mode keeps everything in SQLite and loads the model in-process. It needs the embedded extra and mode = "embedded" in the config before init. The second line writes a new config, so on a machine that already has ~/.collivind/config.toml add the line under [collivind] yourself instead:

uv tool install "collivind-memory[embedded] @ https://github.com/maiiasleptcova/collivind/releases/download/v0.12.0/collivind_memory-0.12.0-py3-none-any.whl"
mkdir -p ~/.collivind && printf '[collivind]\nmode = "embedded"\n' > ~/.collivind/config.toml
collivind init
  • In docker mode, collivind init starts the containers (or uses Qdrant and Neo4j already running) and registers the MCP server for every supported agent it finds installed, plus the hooks (Claude Code, Codex) or the capture plugin (opencode).
  • More on embedded mode and moving data between modes.
  • Codex runs hooks only after you review and trust them.
  • collivind status checks backends, containers, hooks and MCP registration, and exits 1 if anything is broken.

Read and tidy your memory in the browser.

collivind web opens a local UI on 127.0.0.1:8765 over the same store your hooks and agents use.

Search or browse, create and edit memories inline, or forget one for good after a confirmation. Entity and tag chips are clickable and search for that name. Each memory has a Details disclosure with its project, source, confidence, tags, version chain, validity window and session. The header says which store you are reading, docker or embedded.

Loopback only and without authentication: anything that can reach the port can read the whole store.

Measured, with the conditions attached

Retrieval. On LongMemEval-S session retrieval, Collivind finds the right session in the top 5 for 98.0% of the 500 questions (standard uncleaned split, raw mode: the default bge-small embedding model run locally, no LLM, no reranking). This is retrieval recall, not answer accuracy. Method, per-question results and caveats are in BENCHMARKS.md. We publish no comparisons with other memory tools, since they measure different things.

Search latency. With 10,000 memories, median search takes 32 ms in embedded mode and 65 ms on Neo4j + Qdrant, median of the repository's seeded benchmark on an Apple-silicon laptop, embedding time excluded.

Open source, MIT licensed

Everything on this page is in the MIT-licensed repository: the graph and vector memory, hooks for every agent, the MCP tools and CLI, the web UI, lossless export and import, migrate between modes, and sync through a git repo for sharing with a team.

The roadmap says single-user memory, export and sync stay free. A team edition with a shared server and permissions is in development; it is not available or for sale.
